## 4.1 这一节的组织方式

第二次作业的 5 项要求，拆开看是三种活：把需求翻译成界面（原型 40%）、把界面翻译成结构和数据（概要设计 40%，其中含 UML 与数据库设计）、把 13 个人的动作变成可核查的记录（协作记录 20%）。第三种活最容易被写成"我们开了很多会"，所以我们从一开始就把它当成一个交付物来做：有 owner、有模板、有截止时间、有 GitHub 痕迹。

本阶段按**交付物**而不是按"工种"分成五条工作线，每条线 1 名主责、1–2 名协作，每个文件只有一个 owner：

| 工作线 | 主责 | 协作 | 本阶段交付物 |
| --- | --- | --- | --- |
| 项目管理与仓库 | 林诗怡 | 刘翠华、阿合加依娜尔 | 仓库、Projects 看板、周计划、分工表、PR 合并、博客发布检查 |
| 原型设计 | 谢慧彬 | 王凯凤、阿合加依娜尔 | 墨刀/Axure 原型（11 个页面场景，实现为 8 视图 + 2 弹窗）、页面清单、UI 规范、交互说明 |
| 系统设计 | 刘翠华 | 姜思源、赖彦然、张润、吴佳仪、王恩嘉 | 系统设计说明书 9 章、5 类 UML 图、部署与测试设计 |
| 数据库设计 | 李青容 | 陈薇薇、刘翠华、松格拉 | ER 图、关系模型、表结构、ORM 映射、数据字典 |
| 领域 Agent 设计 | 松格拉 | 赖彦然、吴佳仪 | 规则引擎、知识库条目、检索与理由生成、Agent 集成时序 |

**为什么按交付物分，而不是按第一次的四个小组直接搬？** 第一次的"开发与知识库组"有 6 人，如果第二次还让他们只做"开发准备"，这次作业里就没有他们的交付物，GitHub 上也不会有提交；反过来，原型和两份说明书会全部压到文档组和前端两三个人身上。按交付物分线，每个人至少是一个文件的 owner，提交内容和分工表能一一对上。

**文件 owner 制**：owner 决定内容、发起 PR、回应评论；协作人可以改，但必须走 PR。这样最后不会出现"群里有 5 个最终版、不知道哪个算数"。

### 4.2.4 计划怎么保证不烂尾

1. **每周只承诺一个可演示增量**。做不完的进 backlog，不挤占下周关键路径；连续两周未完成的卡片，队长必须砍范围或加人。
2. **P0 优先**。FR-01~FR-11、FR-13、FR-14 是验收底线；FR-12（历史记录）可以晚到 W4/W5，P1 的性能优化可以延后。
3. **范围变更走 Issue**。谁提变更谁写 Issue，写清楚"改什么/为什么/影响哪几个模块/要不要延期"，队长确认后再动，不在群里口头改。
4. **每周日 21:00 复盘**。只看四件事：本周产出了什么、没完成的原因、下周承诺什么、需要谁支援。会议不超过 30 分钟。
5. **留缓冲**。W9 不排新功能；期末周不接新需求。计划里预留的缓冲不是"偷懒"，是给联调和验收留的。

## 4.3 开发分工

### 4.3.1 第一次和第二次的分工要不要一样？

**结论：不需要一样，也不应该完全换一套。我们的做法是"角色主线不变、阶段交付重排"。**

- **不变的是模块 ownership**：后端还是赖彦然、前端还是谢慧彬和王凯凤、知识库还是松格拉、文档还是刘翠华、项目管理还是林诗怡。第三次作业进入编码时，大家不用重新熟悉彼此负责的部分。
- **变的是本阶段的交付物**：第一次是需求、调研、答辩，第二次是原型、系统设计、UML、数据库。所以第二次新增了"章节 owner""UML owner""数据库 owner"，第一次的"PPT 答辩组"在本次只保留 2 人做 UI 规范和答辩大纲，其余人转到设计文档与数据库。
- **表里保留三列**（第一次角色 / 第二次角色 / 后续开发角色），助教能一眼看出谁一直在负责什么、这次为什么调整，而不是临时拼凑。

如果完全照搬第一次的四个小组，会出现两个问题：一是 40% 的原型和 40% 的设计集中在少数人身上，质量风险高；二是第 5 条"每个成员都要有 GitHub 贡献记录"无法满足——开发组没有本次交付物，就没有可提交的文件。按设计交付物重排，是为了让分工和提交记录对得上。

### 4.3.4 关键路径与负载

- 赖彦然（后端/Agent），备份王恩嘉；

### 4.6.5 贡献核验

在仓库根目录执行：

```bash
# 1. 看每个作者的提交数，应该是 13 行
git shortlog -sne --all

# 2. 看本次作业窗口内的作者与邮箱，检查有没有重复/陌生身份
git log --since=2026-11-03 --until=2026-11-10 \
  --format='%an <%ae>' | sort | uniq -c | sort -rn
```

GitHub 页面检查：

1. 仓库 → **Insights → Contributors**，应显示 13 人；
2. 每个成员的 Profile → **Contributions** → 选中 2026 年 → 能看到本仓库的绿色方块；
3. 每个成员的 PR 状态是 **Merged**，对应 Issue 是 **Closed**；
4. 仓库 **Insights → Commits** 按作者筛选，每人至少 2 条。

如果某个成员没有显示贡献，按顺序查：

- **邮箱不匹配**：`git log` 里的邮箱不是他 GitHub 账号绑定的邮箱。解决：GitHub → Settings → Emails 添加该邮箱；本地 `git config user.email` 改成绑定邮箱；已提交的用 `git commit --amend --reset-author --no-edit`（只对自己未合并的分支）。
- **只在分支、没合并**：贡献图只统计默认分支和已合并 PR，先把 PR merge 掉。
- **仓库是 private**：贡献图只对有权限的人可见。改成 public，或把老师/助教加为 collaborator。
- **用别人电脑提交**：author 是别人，贡献算不到本人。必须用自己的 GitHub 账号提交（Web UI 最稳）。
- **一个 commit 传了 13 个文件**：其他人没有贡献。必须各自提交自己的文件。

### 4.6.6 贡献不是刷 commit

我们定的规矩是：**每个 commit 对应一个真实交付物**，不建空 commit、不改空格刷记录、不把别人的文件复制一遍再提交。队长看 diff，每周抽查一次。贡献图是结果，不是目的；如果某个文件是两个人合写的，提交人要在 PR 描述里写清楚合作者，答辩时能说清自己写了哪部分。
