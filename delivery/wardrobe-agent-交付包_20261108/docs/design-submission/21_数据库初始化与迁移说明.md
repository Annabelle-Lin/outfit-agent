# 数据库初始化与迁移说明

## 一、数据库环境

系统使用 SQLite 作为数据库，通过 SQLAlchemy 2.x 进行访问与管理。数据库文件默认位于用户主目录下的 `.wardrobe/wardrobe.db`，这样设计是为了避免项目目录在某些环境下没有写权限。数据库连接串由 `app/config.py` 生成，也支持通过环境变量 `DATABASE_URL` 覆盖，因此保留了切换到其他数据库的能力。连接 SQLite 时设置 `check_same_thread=False`，以适配 FastAPI 的多线程访问。

## 二、初始化机制

数据库初始化由 `app/db.py` 中的 `init_db()` 函数承担，该函数在应用启动的生命周期事件中被调用，时机晚于规则库加载、早于知识库索引构建。其核心语句 `Base.metadata.create_all(bind=engine)` 会依据全部 ORM 实体类的定义，自动检查并创建缺失的表，对已经存在的表不会重复创建或清空数据，因此重复启动应用是安全的。

会话管理由 `sessionmaker` 生成的 `SessionLocal` 工厂提供，接口层通过依赖注入函数 `get_db()` 获取数据库会话，在请求结束时统一关闭，保证连接不泄漏。

## 三、轻量迁移机制

项目没有引入独立的迁移框架，而是针对迭代中新增的字段实现了三个轻量迁移函数，在启动时随 `init_db()` 或模块加载时执行。

`_ensure_user_columns()` 用于给已存在的用户表补齐城市、性别、风格、账号、密码摘要等新增列。它先通过 SQLAlchemy 的检查器读取现有列名，再对缺失列执行 `ALTER TABLE ADD COLUMN`，由于 SQLite 不支持 `ADD COLUMN IF NOT EXISTS` 语法，列存在性判断在应用层完成。

`_ensure_session_columns()` 用同样的方式给会话表补齐降雨概率列。`_ensure_columns()` 则处理反馈表的证据列与会话表的天气来源列，它通过 `PRAGMA table_info` 读取表结构后决定是否补列，整体包裹在异常处理中，避免迁移失败阻断启动。

这套机制的特点是只做增量加列、不做删列与类型变更，与课程项目的演进节奏匹配；每次迁移都先判断后执行，对全新数据库和老数据库都能平滑处理。

## 四、手工建表脚本

除 ORM 自动建表外，素材包另附 `sql/wardrobe_schema.sql`，内容为依据 ORM 模型反推的七表 SQLite 建表语句，包含主键、索引、唯一的会话外键以及字段默认值。需要在不启动应用的情况下独立建库时，可执行 `sqlite3 wardrobe.db < wardrobe_schema.sql`。脚本开启外键约束并使用 `IF NOT EXISTS`，可重复执行。

## 五、示例数据导入

系统提供 `scripts/import_sample_wardrobe.py` 脚本，可把 `衣橱示例数据/` 下五十件已标注衣物一键入库，脚本内含去重与回读校验；`seed_demo.py` 用于生成演示数据；`scripts/clear_clothes.py` 用于在演示前重置衣物数据。这些脚本与建表机制配合，构成完整的数据库初始化与演示数据准备流程。

## 六、现有实现与计划设计的区分

当前七张表及全部加列迁移均为已实现并经代码核验的内容，建表 SQL 是对现有 ORM 定义的等价翻译，而非未落地的计划。数据库设计说明书中若出现新的表或字段设想，应明确标注为计划设计；本说明描述的初始化与迁移流程则全部对应真实代码路径。
