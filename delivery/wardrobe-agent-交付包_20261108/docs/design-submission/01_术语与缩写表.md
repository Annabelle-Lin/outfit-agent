# 术语与缩写表

> 本表对《系统设计说明书》《数据库设计说明书》及团队博客中出现的缩写、专有名词先行定义，正文首次出现时不再重复解释。所有定义均与本项目代码实现一致。

## 一、通用技术缩写

| 缩写 / 术语 | 全称 / 英文 | 本项目中的含义 |
|---|---|---|
| API | Application Programming Interface，应用程序编程接口 | 后端对外暴露的 HTTP 接口，统一前缀 `/api/v1`，当前共 34 个端点 |
| HTTP | HyperText Transfer Protocol，超文本传输协议 | 前后端通信协议，本项目使用 HTTP/1.1 |
| REST | Representational State Transfer，表述性状态转移 | 本项目接口风格，以资源路径加 HTTP 方法（GET/POST/PUT/DELETE）组织接口 |
| JSON | JavaScript Object Notation | 全部接口请求体、响应体及数据库多值字段的承载格式 |
| SSE | Server-Sent Events，服务器发送事件 | 知识问答流式输出机制，响应类型 `text/event-stream`，服务器逐帧推送文本增量 |
| CORS | Cross-Origin Resource Sharing，跨源资源共享 | 后端通过 `CORSMiddleware` 允许前端跨端口、跨协议访问 |
| SPA | Single Page Application，单页应用 | 前端形态，全部页面集中于 `frontend/index.html`，靠 JavaScript 切换视图 |
| CRUD | Create、Read、Update、Delete，增删改查 | 衣物、用户等资源的四类基础操作 |
| 端点 Endpoint | — | 一个具体的接口地址与 HTTP 方法组合，如 `POST /api/v1/clothing` |
| 中间件 Middleware | — | 在请求到达路由前统一执行的层级，本项目用于登录鉴权 |

| 事务 Transaction | — | 一组要么全部成功要么全部回滚的数据库操作，本项目通过 `db.commit()` 提交 |

## 三、Agent 与人工智能相关术语

| 缩写 / 术语 | 全称 / 英文 | 本项目中的含义 |
|---|---|---|
| Agent | 智能体 | 本项目核心，指能理解用户请求、结合规则与知识完成穿搭推理并组织回答的对话式穿搭智能体 |
| LLM | Large Language Model，大语言模型 | 本项目接入智谱 GLM-4-Flash，负责自然语言解释与问答生成，不承担可行性判定 |
| GLM-4-Flash | — | 智谱 AI 提供的免费大语言模型，经 `app/agent/llm.py` 调用 |
| RAG | Retrieval-Augmented Generation，检索增强生成 | 先从知识库检索相关片段，再把片段作为参考资料交给 LLM 生成回答的技术路线 |
| BM25 | Best Matching 25 | 经典词法检索算法，本项目通过 `rank-bm25` 库实现知识库片段召回 |
| RRF | Reciprocal Rank Fusion，倒数排名融合 | 多通道检索结果的融合算法，本项目用于合并原词通道与同义词扩展通道的排名 |
| 分词 Tokenization | — | 把文本切分为词项的过程，本项目优先使用 jieba，缺失时退化为逐字切分 |
| jieba | — | 中文分词库，用于 BM25 索引构建与查询分词 |
| 规则引擎 Rule Engine | — | 本项目推荐主链路，依据 JSON 配置的硬过滤与打分规则完成可解释、可复现的搭配推理 |
| 硬过滤 Hard Filter | — | 规则引擎第一层，对违反温度、场合、色彩等硬性条件的组合直接淘汰 |
| 打分 Scoring | — | 规则引擎第二层，以基础分 60 分起评、按各规则加权得到 0–100 的方案分 |
| 降级 Degradation | — | 外部服务（LLM、天气）不可用时退回本地模板或检索结果的机制，保证系统不中断 |
| Function Calling | 函数调用 | 智能体调用外部工具的能力；本项目的工具调用在后端进程内以函数方式实现 |
| 启发式 Heuristic | — | 不依赖模型的本地经验算法，本项目用于图片主色识别与品类猜测 |
| 多模态 Multimodal | — | 同时处理文本与图像等多种信息形态，本项目图片属性识别为多模态预留能力 |

## 四、业务领域术语

| 术语 | 含义 |
|---|---|
| 单品 / 衣物 | 衣橱中的一件独立衣物，对应 `clothing_items` 表一行 |
| 搭配 / 方案 Outfit | 由若干单品按规则组合成的一套穿着，如“上装＋下装＋鞋”，对应 `outfit_records` 表一行 |
| 一级品类 | 衣物大类，即上装、下装、外套、连衣裙、套装、鞋、配饰 |
| 二级品类 | 一级品类下的细分类，如衬衫、T 恤、牛仔裤、凉鞋 |
| 暖度 warmth_level | 单品厚薄保暖等级，取值 1–5，1 最薄、5 最厚 |
| 正式度 formality_level | 单品正式程度，取值 1–5，数值越大越正式 |
| 体型 body_shape | 用户身材分类，规则库实际采用梨形、苹果形、H 形、倒三角、匀称五类 |
| 长期偏好 | 用户对色彩、风格、舒适、场合、面料五个维度的稳定倾向，取值 1–10，默认中值 5 |
| 临时偏好 | 单次会话内的色彩（亮色/暗色）与款式（基础款/设计款）倾向，不写入长期画像 |
| 会话 Session | 一次连续对话的上下文容器，对应 `chat_sessions` 表，保存场合、天气、约束与额度 |
| 购前评估 | 对拟购买的新品判断其与现有衣橱的可搭配性、重复度并给出购买建议 |
| 反馈 Feedback | 用户对方案“喜欢/一般/不喜欢”的评价，用于重算长期偏好，且支持撤销 |
| 三色原则 | 一套搭配中主色数量不超过三种的配色规则，配饰不计入 |
| 胶囊衣橱 | 以少量高利用率单品互相搭配的衣橱管理理念，是本项目知识库来源之一 |
| 知识库 | 存放服装色彩、版型、面料、礼仪、胶囊衣橱等领域知识的 Markdown 文档集合，位于 `data/s3_kb/` |

## 五、口径说明

其一，代码注释中出现过“沙漏形、矩形”等体型说法，但规则库 `body_rules.json` 实际加载的是梨形、苹果形、H 形、倒三角、匀称五类，全部文档以规则库为准。其二，早期 README 提到“和风天气”，当前代码实际接入的是零密钥的 Open-Meteo 接口，文档以当前实现为准。其三，`API_CONTRACT.md` 冻结于 v0.4 版本，记录 22 个接口；其后新增了图片上传与识别、流式问答、反馈影响与撤销、数据清空等端点，当前实际为 34 个，接口清单以本素材包 `04_接口清单表.md` 为准。
