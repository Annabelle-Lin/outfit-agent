# 非功能需求与安全设计

## 一、安全性需求

系统在账号、传输与数据访问三个层面做了安全设计。账号层面，用户密码不做明文存储，注册时由安全模块使用 PBKDF2-HMAC-SHA256 算法配合每用户随机盐生成不可逆摘要，迭代次数为十二万次，数据库中只保存摘要；登录校验时使用恒定时间比较，降低时序侧信道风险。

会话层面，登录成功后签发 HMAC 签名的无状态令牌，令牌内含用户标识与过期时间，有效期三十天，签名密钥优先取环境变量、其次取本地自动生成的密钥文件。每次请求由鉴权中间件校验令牌，无效或过期返回 401。数据访问层面，所有业务接口以令牌中的用户标识为准，中间件同时校验请求参数与请求体中出现的用户标识，不一致即判定越权并返回 403，资源级操作还通过归属校验函数二次确认，确保用户只能读写本人数据。

## 二、可靠性与降级需求

系统对外部依赖均设计了兜底路径，保证外部服务异常时主功能不中断。大模型当前尚未接入，知识问答以检索片段原文展示、推荐回复以模板文案呈现，这是现阶段默认形态而非临时降级，待模型接入后再启用生成式回答。天气服务异常时返回模拟数据并标注来源，城市无法识别时明确提示而非伪造温度，天气完全未知时不执行天气相关的过滤与打分。图片识别在视觉模型未启用时使用本地启发式。所有结果都显式标注来源与实现方式，用户始终能区分实时数据与兜底数据。

## 三、性能需求

系统采用轻量技术栈以满足普通设备上的流畅运行。规则库在启动时一次性加载并在进程内复用，避免每次请求重复读取文件；天气查询结果在内存中缓存三十分钟，减少外部调用；知识库索引在启动时一次构建，检索直接复用。数据库基于本地 SQLite 文件，单用户场景下查询延迟低，列表接口统一分页，避免一次返回过多数据。接口默认异步处理；目标方案中的流式问答通过 SSE 逐字推送以降低首字等待感，该能力随大模型接入一并实现，当前未启用。

## 四、易用性需求

前端采用统一的莫兰迪配色与一致的卡片、表单、导航样式，降低学习成本。表单提供品类联动、颜色点选、快捷标签与输入联想，必填项未完成时按钮置灰并给出提示。对话入口当前以静态原型演示其界面与目标交互，用户无需理解系统内部规则即可体验。异常都以可读文案说明，不暴露技术错误码。

## 五、可维护性与可追溯性

规则与业务代码解耦，硬过滤、打分、体型规则和标签枚举均以 JSON 配置文件维护，调整规则无需修改程序。每条规则带来源字段、每条知识带出处标注，推荐理由点关联规则编号，使每一次结论都可追溯。接口层、推理层、数据层职责清晰，Pydantic 模型与 ORM 模型分离，便于独立演进。数据库表结构演进通过轻量迁移函数处理，老库可平滑补齐新增列。

## 六、数据一致性与隐私

多值字段统一以 JSON 结构存储并由 Pydantic 校验，保证结构一致；反馈偏好采用按全部反馈重算的幂等机制，撤销反馈后分数可精确回退，避免增量更新累积误差。隐私方面，外部密钥只通过环境变量与 `.env` 注入，不写入代码；真实 `.env` 不提交版本库；用户数据清空接口支持按范围删除，保留账号与偏好的同时可清除业务数据。
